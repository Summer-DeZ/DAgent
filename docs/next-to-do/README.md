## 执行规则

1. 本次用户明确要求“只重构、不扩展”；这优先于讨论早期出现的功能设想。
2. 不创建测试代码、模拟模型、演示入口或测试构建目标；只使用正式构建和真实功能运行，临时验收材料仅放 `temp/`。
3. `.hpp` 仅放 `src/public/`，`.cpp` 仅放 `src/private/`；冻结 TUI 原语保持不变。
4. 不默认启用子 Agent 实施；有新的明确授权才采用并行代理。
5. 完成按任务推进，不在完成后反复静态 review。出现实际失败时再针对性定位。
6. 不将现有源码中的其他缺陷自动加入重构范围；发现差异先记录，在保持清单中明确归类。
7. 不静默添加守护进程、任务系统、通用插件平台或持久化队列。
8. 所有任务初始为“未开始”。构建通过、代码已写、真实验收通过是不同状态。
9. 例行命名和局部算法可自行决定；本文已经锁定的产品语义、依赖方向、对象所有权和协议语义不得自行改变。
10. 如后续源码已变化，先核对当前 diff 和保持清单；不要覆盖用户改动，不把旧行号当作修改位置。

## 无需猜测的范围

业务范围、状态所有者、依赖方向、记录字段/顺序、恢复副作用、线程归属和进程生命周期均按本文档执行。
记录路线以 L01–L23 为逐项清单，实施者不能自行选择哪些事件落盘或回放时执行什么。
局部 C++ 语法、容器实现和实际编译诊断仍需工程判断；文档不承诺任意模型可以零判断生成正确代码。
遇到明确规格冲突时列出条款与源码证据；能保持约束的实现修正自行完成，产品行为变更不能靠猜测加入。

## 恢复一次中断的实施

读取 [任务状态表](implementation-tasks.md#1-任务图与状态)，找到第一个依赖满足且未验收完成的任务。
核对该任务已有文件和真实证据，补完剩余部分；不要重复创建已经存在的模块或重做通过的场景。
任务记录写明：版本、完成内容、构建结果、实际运行结果、证据位置、未完成项与下一任务。

## 最终交付

最终应得到现有功能的两个正式进程：`dagent` 前端与它独占的 `dagent-backend`。
核心业务可独立理解；UI 不拥有执行状态；记录恢复与历史显示职责分离；原有 CLI、工具与交互能力保持。
当前实现说明仍见 [docs/design](../design/)。仅在对应任务完成后，将已实现的事实更新到该目录。
